La cota procede de `GET /v11/deployments/{id}/builds → builds[].output[].lambda.timeout`, por `functionName`, path, digest y deployment. El CLI oficial la usa para inspeccionar deployments ([source fijado](https://github.com/vercel/vercel/blob/c628be7835e03a965b93e9cf9e2bd5ac2acbf5eb/packages/cli/src/commands/inspect/index.ts)). El listado de archivos puede devolver 404 en un deployment Git; en ese caso la correlación explícita es entre nombres de funciones v13 y outputs v11. Un error distinto o una cobertura desigual detienen el colector/verificador.

**No se usó `default=300`** del proyecto, el tiempo del build, Node `22.x`, logs vacíos ni el `maxDuration=60` del código nuevo para acotar una función vieja. Los 300 segundos son una observación de esos deployments fechados; deben leerse otra vez si cambia cualquier destino. Vercel documenta que [termina la invocación al superar su duración configurada](https://vercel.com/docs/functions/configuring-functions/duration).

La evidencia privada `drain-four-projects.json` conserva 89 aliases y las cuatro configuraciones WAF actuales. Ambos proyectos históricos tienen una denegación activa de todo `path` que empieza por `/`; los proyectos de producción deniegan los hosts no canónicos. Esto debe corroborarse otra vez, incluyendo posibles bypasses, SSO, cambios de aliases y accesos internos. No basta con que el deployment señalado como Production sea seguro. Un deployment histórico que resulte alcanzable requiere contención efectiva y su propio timeout; no se reemplaza por el máximo del deployment nuevo.

## Cierre por fases, preparado y sin aplicar

1. Completar los preflight no disruptivos del runbook. El catálogo/Admin siguen operando. Sólo después de `PRE_CUTOVER_READY=YES` en la etapa futura se confirma temporalmente que John y los otros escritores externos están detenidos.
2. Conservar snapshot y hash vigentes de las cuatro WAF/aliases/deployments y de Rules. Generar propuestas de cierre con `node scripts/release-cutover/cli.mjs propose-closure <snapshot.json> store` y `admin`. `storeLegacy`/`adminLegacy` sirven para validar/preparar contención; si la denegación existente ya contiene todas las entradas, conservarla sin añadir una regla redundante.
3. La regla temporal inicial bloquea **todos** los métodos distintos de GET/HEAD/OPTIONS en cada proyecto productivo, sin excepción de header. Además bloquea la ruta del reconciliador en Tienda y la firma ImageKit en Admin por path o raw_path. Catálogo público y GET administrativos conservan sus reglas anteriores. No se cambia ninguna regla de órdenes retiradas ni se añade bypass/skip/IP persistente.
4. Preparar el control `operations/webStockCutover` con `schema:1`, `state:'closed'`, `revision` de 16–100 caracteres `[A-Za-z0-9_-]` y `updatedAt` Timestamp del servidor. La variante de Rules exige control abierto para escrituras de clientes; no permite que un cliente lo cambie. Aplicarla sólo tras verificar el source realmente instalado y preservar las restricciones de órdenes y reservas.
5. Registrar `serverCommitMs` del cierre, readback fuerte y revisión. Las guardas leen el documento sin caché y fallan 503 si falta, es inválido o la lectura falla. El protocolo distingue `open` (operación normal), `closed` (todos los escritores detenidos) y `reconciling` (sólo conciliación de servidor; compras, Admin y clientes directos siguen cerrados). La lectura es el punto de admisión: lo admitido antes del cierre puede finalizar. No es un lock que interrumpa una transacción o MP ya iniciados. Los escritores viejos no conocen el control; necesitan WAF/Rules y drenaje.
6. El instante inequívoco de cierre total es el máximo entre commit del control y los instantes de vigencia/readback de **todas** las barreras, incluyendo escritores externos. No medir desde que se hizo clic o empezó una solicitud de configuración. Si no se puede demostrar propagación/vigencia, no existe un instante de cierre acreditado.
7. Ejecutar el drenaje siguiente antes de integrar/promover una pareja nueva. Después, Admin compatible primero y Tienda después por el canal prebuilt. Mantener cierre y reservas existentes.

## Smokes del candidato y WAF

Sólo tras comprobar metadata del deployment candidato, build stamp y guardas cerradas se prepara `propose-candidate <closed-waf.json> <candidate.json>`. `candidate.json` exige host literal `.vercel.app`, deployment ID, HEAD, TREE y `guardsClosed:true`. Es un input a revisar contra evidencia, no atestación automática.

El delta resta dos excepciones a las denegaciones correspondientes: host candidato exacto + path y raw_path idénticos + método exacto + header `x-mutter-release-action` permitido. Se transforma sólo `mutter-noncanonical-host-deny`, `mutter-api-get-deny` y la nueva regla temporal. Las demás reglas permanecen. El host canónico viejo sigue cerrado. No se incluye el valor del bearer en reglas ni artefactos. El motor WAF tiene operadores insensibles a mayúsculas; el handler valida acción/método estrictamente y rechaza variantes. La matriz local modela esa diferencia, sin atribuirle al WAF garantías del código.

| Smoke | Método, host y path exactos | Headers/body | Efecto permitido |
| --- | --- | --- | --- |
| Runtime checkout | POST; host literal candidato; `/api/create-mp-preference` | `x-mutter-release-action: runtime-attestation`; bearer release dedicado; sin body comercial | Recibo de runtime; cero Firebase/MP/stock |
| Runtime reconciliador | GET; mismo host; `/api/internal/web-stock-reconcile` | Misma acción y bearer release, **no** bearer Cron | Recibo runtime; no barrido ni recibo mantenimiento |
| Quote | POST; mismo checkout | `read-smoke`; bearer release; body de `action:'quote'` y selecciones reales autorizadas para la etapa futura | Lecturas de producto/reserva; ninguna escritura ni proveedor |
| Disponibilidad | POST; mismo checkout | `read-smoke`; bearer release; `action:'availability'` y IDs según contrato existente | Sólo disponibilidad real |
| Catálogo básico | POST; mismo checkout | `read-smoke`; bearer release; exactamente `{"action":"catalog"}` | Lectura acotada; recibo con número de filas |
| Órdenes Admin | POST; mismo checkout | `read-smoke`; bearer release; exactamente `{"action":"admin_read"}` | Lectura acotada; sólo conteo, sin devolver datos de clientes |
| Lectura Admin API | GET; `mutter-games-admin-api-prod.vercel.app`; `/api/admin/products` u otra ruta autorizada pertinente | Token de sesión Admin válido, sin crear usuario ni iniciar Auth anónima | Lectura normal sin edición; conservar únicamente recibo/proyección no sensible |

Nunca `start`, `status`, `verify`, navegación SPA, firma ImageKit, login/registro, compra/pago/preferencia real, ni productos QA. No transformar un HTTP 200 en prueba de ausencia de escrituras: las regresiones de emulador/JS emitido y su contador de escrituras acreditan el comportamiento; al aplicar se contrasta evidencia del proveedor y la frontera real. WAF no autentica el secreto: un header forjado sólo puede alcanzar una frontera que responde 401/400/405 sin negocio.

## Cota y evaluador

`collect.mjs <deployment-manifest.json>` hace sólo GET de metadata; exige IDs explícitos dentro de los cuatro proyectos y no invoca las aplicaciones. El manifiesto enumera `{deployments:[{projectId,deploymentId}]}`. El CLI instalado sólo transporta estas lecturas; no se usa como constructor ni publicador. Los outputs conservan comandos/códigos reales, incluyendo el 404 conocido de `/files`.

`cli.mjs verify-drain <evidence.json>` **no espera ni aplica nada**. Comprueba existencia/hash de todos los archivos de evidencia (paths relativos al paquete, sin escapes/symlinks externos), liga los snapshots al recibo del colector y evalúa consistencia de la línea temporal. La función pura puede devolver `DRAIN_PLAN_CONSISTENT`, con `remoteDrainVerified:false`; el CLI conserva **exit 1 `NOT_VERIFIED`** porque esta preparación no dispone de un adaptador que acredite cobertura real completa de logs, invocaciones y escrituras. Los contadores/booleanos aportados por un operador no se convierten en atestación. El expediente se completa y contrasta manualmente contra fuentes primarias en la etapa autorizada. Requiere:

- los snapshots v13/v11/v6 de funciones actuales, con correlación completa y timeout entero positivo por función; ningún writer desconocido;
- inventario exacto de funciones y demás escritores, cobertura de cuatro proyectos y documento central cerrado;
- seis cierres (cuatro proyectos, Firestore directo, escritores externos), revisión común, pruebas/hashes y hora efectiva;
- margen técnico separado en desfase de reloj, terminación y propagación, con justificación y fuente. No hay un margen constante que se invente como hecho;
- `deadline = max(cierres efectivos, commit servidor) + max(lambda.timeout) + margen` y tiempo ya transcurrido;
- logs completos, sin muestreo, frescos, con ventana que cubra posibles invocaciones previas, cero invocaciones activas/admisiones nuevas y pruebas positivas de cierre de cada superficie;
- una ventana de quietud posterior a `deadline`, justificada por evidencia de reloj/propagación/ingesta, y ausencia de escrituras en esa ventana. Las operaciones admitidas antes del cierre pueden escribir antes del vencimiento de su cota: conservar y explicar esas finalizaciones válidas; nunca deshacerlas, recerrar artificialmente una revisión ni borrar reservas para obtener verde.

`observation.positiveClosureProbeScopes` es un índice de evidencia positiva por superficie, no una orden de ensayar escrituras comerciales ni de crear datos QA. En la futura etapa autorizada se completa así:

- **APIs Vercel:** comprobar la denegación WAF con método/ruta inventariados, cuerpo vacío o inválido, sin IDs comerciales ni credenciales de compra/Admin. Para firma y reconciliador, GET sin credencial; nunca enviar `CRON_SECRET`, un body válido, un token Admin/cliente ni otro secreto que permita escribir si fallara el cierre. Correlacionar el rechazo con el evento WAF primario por proyecto, regla, host, método, path, request ID y tiempo, y con el readback de configuración vigente. Un 401/400 de la aplicación o un 403 sin procedencia demostrable no acredita que WAF cerró la entrada. Estas solicitudes prueban únicamente el bloqueo observado de esas entradas; no prueban por sí solas cobertura de otros hosts ni ausencia de invocaciones en vuelo.
- **Firestore directo:** leer source/hash/version de las Rules efectivamente instaladas y el control cerrado con su Timestamp/revisión; comparar los bytes con la variante aprobada y ejecutar sus regresiones locales en emulador. No intentar una escritura productiva, ni siquiera con cantidad cero o sobre un documento QA. La regresión local acredita la lógica de esos bytes; el readback acredita qué versión está instalada. Ninguno por separado prueba propagación, ausencia de otra autoridad ni quietud del servidor: conservar la evidencia primaria adicional requerida para esos puntos.
- **Escritores externos/Admin SDK/consola:** inventario y readbacks de configuración/autoridades/procesos pertinentes, confirmación temporal de los responsables y evidencia de su cese y de ausencia de trabajo activo. No probar el cierre creando productos, cambiando cantidades o ejecutando scripts mutadores. Rules y WAF no contienen esta autoridad; una declaración humana sin inventario/cobertura suficiente no cierra esa superficie.

El contrato productivo siguiente debe resolver antes de `PRE_CUTOVER_READY` el canal y alcance autorizados para estos readbacks/eventos, la cobertura completa de logs e invocaciones/escrituras y la justificación medible del margen y quietud. Este target no concede esos accesos ni acredita esos pendientes. Si falta una fuente necesaria, el campo de scopes no se llena con una suposición: el gate permanece sin verificar.

Los hashes de un JSON no son firmas de Vercel/Firestore. El evaluador verifica integridad local y consistencia de recibos; el responsable de la etapa debe verificar su procedencia y contenido primario. Un contador manual cero, logs vacíos o evidencia muestreada no cumplen el gate. La falta del adaptador es un límite de automatización; la falta de cobertura primaria es un bloqueo del drenaje. No son equivalentes ni excepciones aceptadas.

En la etapa de aplicación autorizada, la ausencia del adaptador no impide una verificación humana documentada. El responsable debe conservar el `NOT_VERIFIED` y exit 1 reales del CLI, su resultado de integridad y `DRAIN_PLAN_CONSISTENT`, y emitir un acta separada, fechada, que identifique responsable, revisión del control, deployments/funciones y cada recibo primario por fuente/hash. Debe contrastar directamente los seis cierres efectivos, identidad/cota por función, cobertura completa no muestreada de admisiones e invocaciones, finalizaciones previas válidas, margen justificado y ausencia de escrituras durante la quietud posterior a `deadline`. El acta declara el resultado de esa revisión primaria, sin cambiar el resultado del programa ni llamarlo PASS automático. Un fallo de integridad/consistencia, una superficie sin cobertura o una inferencia basada sólo en logs vacíos mantienen el cierre y bloquean la aplicación: no se suplen con el acta ni con tiempo transcurrido.

Los fixtures positivos son sintéticos, identificados como tales, y sólo prueban el evaluador. No fabrican un drain productivo ni garantías de MP. `node --test scripts/release-cutover/policy.check.mjs` cubre los predicados generados y los rechazos por falta de tiempo, metadata, cobertura, cierre, pruebas positivas, margen y escrituras nuevas. La matriz WAF es un modelo local de operadores usados, no validación remota del motor; antes de aplicar se valida el payload en la plataforma y se conserva readback exacto.

La matriz contra snapshots reales se reproduce con `node scripts/release-cutover/verify-snapshot-matrix.mjs <drain-four-projects.json> <provider-snapshots.json>`. Recorre todos los aliases del snapshot más los hosts de deployment y un host inválido, compara los predicados de cierre y limita la excepción de candidato sintético por host/método/path/raw_path/header. También modela la fase `reconciling` contra esas reglas: GET del reconciliador en hosts explícitos, compras y métodos mutadores aún denegados. El recibo enumera el número de comprobaciones y deja `remoteApplied:false`, `remoteDrainVerified:false`. No usa las reglas reales como fixture de un supuesto despliegue efectuado.

El expediente para `verify-drain` usa `schema:1`, `snapshots` del colector y `metadataEvidence:{source,sha256}` apuntando al archivo de ese recibo. Cada `control.evidence`, `closures[].evidence`, `inventory.evidence`, `margin.evidence`, `quiescence.evidence`, `observation.evidence` y `writeObservation.evidence` referencia otro archivo por el mismo formato. Las rutas son relativas a la carpeta del expediente. Conservar logs/proyecciones sin cuerpos comerciales, tokens ni secretos. El test del evaluador muestra el schema de tiempos/contadores, pero **no se copia ese fixture como evidencia de producción**. La inexistencia de archivo, hash distinto, escape de path o metadatos de otra función fallan antes de analizar la línea temporal.

## Reapertura y continuidad

No escribir cantidades, reservar/liberar manualmente ni borrar pedidos para abrir. El cambio del control a `open` sólo admite trabajo posterior; preserva reservas y pagos. Antes, verificar pair Admin/Tienda, runtime remoto, índice READY, prebuilt realmente aplicado y WAF/SSO. Para acreditar Cron sin abrir compras/Admin se usa deliberadamente `reconciling`: el servidor acepta la conciliación autenticada, mientras los otros writers y Rules exigen `open`. `propose-reconciling <waf.json> <phase.json>` prepara sólo la excepción GET exacta de reconciliación en uno o dos hosts/deployments explícitos de la transición, con revisión común y pareja verificada; no contiene secretos ni bypass. El handler conserva `CRON_SECRET`. Recién tras el gate programado del runbook se pasa a `open`. Recargar completamente las SPAs administrativas viejas cuando se autorice reabrir.

Cada deploy/promoción/rollback exige inventario, configuración efectiva y drenaje nuevos. Un rollback sólo puede ir a una pareja que respete reservas y el control; el código anterior a reservas no es rollback válido. Si hay datos vivos y un gate falla, mantener barreras y evidencias. No eliminar WAF ni abrir el control por vencimiento de un plazo. No declarar Cron operativo por simulación, `--skip-domain`, alias o un disparo manual.

Pendientes remotos expresos: runtime candidato, Rules realmente instaladas, índice READY, secretos instalados, funciones remotas Firebase, otros escritores/IAM/consola, cierre efectivo, logs completos de drenaje, smokes reales autorizados, Cron y observación. Esta preparación no afirma `PRE_CUTOVER_READY=YES`.
